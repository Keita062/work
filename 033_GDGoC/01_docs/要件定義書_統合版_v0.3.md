# 要件定義書：ニーズ把握型サービス提案AI（仮称）

チーム：team analysis

練習お題：Renewal of the world

## 1. プロジェクト概要

### 1.1 プロジェクトの目的

チーム3名（まさい・けーた・ゆうき）で、2026年10月24日（土）・25日（日）の2日間で、採点基準を満たす動くWebアプリを完成させる。

### 1.2 プロジェクトの背景

GDGoC（Google Developer Groups on Campus）の練習お題「Renewal of the world」に対する取り組みである。

### 1.3 プロジェクト前提

- インフラはすべてGoogleのサービスで構成する（採点基準「Google技術の活用」のため）
- 費用は各サービスの無料枠内に収める
- 2日間でのプロトタイプ完成までとし、本番運用・保守は行わない
- 新規開発とする（ジャービス設計メモは参考資料としてのみ扱う）
- 提案の対象はWebサービスに限定する（チーム決定 2026-10-18）
- デモは利用者本人が実際に入力して行う
- 要件の確定と役割分担は、チーム3名の合意で決める

## 2. サービス概要

### 2.1 サービスの目的

ユーザーが自分で探さなくても、自分の目標・状況に合うWebサービスに出会えるようにする。

### 2.2 サービスの背景

Webサービスは数多く存在するが、それぞれ決まったニーズに向けて作られており、ユーザー一人ひとりの目標や状況は把握していない。

### 2.3 AsIs－ToBe

- **ToBe（あるべき姿）**
  - AIとの対話でユーザーの目標・状況を把握できている
  - 把握した内容に合うWebサービスを、理由とともに提案できている
  - 目標・状況が変化したら、提案を更新できている
- **AsIs（現状）**
  - ユーザーの目標・状況を把握できていない
  - 合うWebサービスを提案できておらず、ユーザーが自力で探し比較している
  - 目標・状況が変化しても提案は更新されず、ユーザーが探し直している
- **Gap**
  - ①ユーザーの目標・状況を把握する仕組みがない
  - ②目標・状況に合うWebサービスを探して提案する仕組みがない
  - ③目標・状況の変化に合わせて提案を更新する仕組みがない
- **Issue**
  - ①既存のWebサービスには、ユーザーと対話して目標・状況を聞き取り、記録する機能がないため
  - ②多数のWebサービスを、ユーザーのニーズに紐付けて絞り込む仕組みがないため
  - ③ニーズの変化を検知して再提案する仕組みがなく、一度の提案が固定されたままになるため
- **Solution**：AIがユーザーの目標・状況を継続的に把握し、合うWebサービスを提案するWebアプリを作る（機能の詳細は3章）

### 2.4 対象外

本サービスの範囲は「提案 → ユーザーの承諾 → サービスを開く」までとし、次は行わない。

1. 提案したWebサービスへの登録・ログインの代行（ユーザー自身が行う）
2. 複数のサービスを一つの窓口からまとめて操作すること（ジャービス型）
3. 日本語以外の言語への対応

## 3. 機能要件

2.3 Solutionを実現するために、システムが満たすべき機能を「システムは〜すること」の形で定義する（ユーザーの操作は5章に記載）。

### 3.1 ニーズ把握の対話

ユーザーの目標・状況・興味・悩みを、AIとの対話で聞き取る。

- システムは、対話画面を開いたときに最初の質問を表示すること
- システムは、目標・状況・興味・悩みを聞く質問をGemini APIで生成し、表示すること
- システムは、ユーザーの回答を自由記述のテキストで受け付けること
- システムは、それまでの回答をふまえて次の質問を生成し、4項目すべてについて回答が得られるまで対話を続けること（何をどう聞くかはAIが対話の流れに応じて決める）
- システムは、質問と回答のやり取りを対話ログとして保存すること

入力：ユーザーの回答

出力：質問文、対話ログ

### 3.2 ニーズの整理と保存

対話で聞き取った内容を4項目に整理し、ユーザーの確認を経て保存する。

- システムは、対話の終了後に、対話ログから目標・状況・興味・悩みの4項目を抽出・要約し、ニーズ確認画面に表示すること
- システムは、ユーザーが各項目の内容を修正できるようにすること
- システムは、ユーザーが承認した時点で、修正を反映した内容をユーザープロフィールとして保存すること
- システムは、ユーザーが承認するまで、3.3以降の処理を開始しないこと

入力：対話ログ、ユーザーの修正内容

出力：ユーザープロフィール

### 3.3 サービスの検索・比較

ユーザープロフィールに合うWebサービスを探し、合う順に並べる。

- システムは、ユーザープロフィールをもとに、Webサービス候補データ（4.1）から候補を検索すること
- システムは、各候補がユーザープロフィールの4項目にどれだけ合うかを評価し、順位を付けること

入力：ユーザープロフィール、Webサービス候補データ

出力：順位付きの候補一覧

### 3.4 提案の生成

順位の高い候補を、おすすめの理由を付けてユーザーに提示する。

- システムは、順位付きの候補一覧から上位の最大3件を選ぶこと
- システムは、選んだ各候補について、ユーザープロフィールのどの項目に合うかを示すおすすめの理由をGemini APIで生成すること
- システムは、サービス名・おすすめの理由・URLを提案結果画面に表示すること
- システムは、表示した提案を、提案日時とその時点のユーザープロフィールとともに提案履歴として保存すること

入力：順位付きの候補一覧、ユーザープロフィール

出力：提案（最大3件）、提案履歴

### 3.5 提案したサービスを開く

ユーザーが承諾した提案のサービスを開き、使い始められるようにする。

- システムは、提案結果画面で、ユーザーが提案ごとに承諾できるようにすること
- システムは、承諾された提案のサービスを、URLのリンクから新しいタブで開くこと（提案先サービスとのAPI連携は行わない）
- システムは、提案が承諾されたことを提案履歴に記録すること
- システムは、提案先サービスへの登録・ログインを代行しないこと（2.4 項目1）

入力：ユーザーの承諾

出力：開いたサービス、承諾の記録

### 3.6 提案の更新

ユーザーの目標・状況が変わったときに、提案を作り直し、前回との違いを示す。

- システムは、ユーザーの同意を得たうえで、本サービス内の行動履歴と端末の利用状況を収集すること
- システムは、収集した行動履歴・端末の利用状況とユーザープロフィールをGemini APIに渡し、ニーズが変化したかどうかをAIに判定させること
- システムは、ユーザーからの目標・状況の変化の申告も受け付けること
- システムは、変化を検知した、または申告を受けたら、変化した項目を対話で聞き取り、3.2と同じ手順でユーザープロフィールを更新すること
- システムは、更新後のユーザープロフィールで3.3・3.4を再実行し、新しい提案を生成すること
- システムは、前回の提案との違い（新たに加わったサービス、外れたサービス、変化したニーズの項目）を提案更新画面に表示すること
- システムは、更新前のユーザープロフィールと提案を、提案履歴から削除せずに残すこと

入力：行動履歴・端末の利用状況、変化の申告、前回の提案

出力：新しい提案、前回との違い

### 3.7 提案履歴の閲覧

過去の提案と、そのときのニーズを振り返れるようにする。

- システムは、過去の提案を提案日時の新しい順に一覧表示すること
- システムは、各提案について、提案日時・提案したサービス（サービス名・おすすめの理由・URL）・承諾の有無・その時点のユーザープロフィールを表示すること
- システムは、利用中のユーザー本人の提案履歴だけを表示すること

入力：提案履歴

出力：提案履歴画面

## 4. データ要件

本サービスが保持するデータと、扱わないデータ、データを整形・集計する流れを定義する。保持するデータは、すべてBigQueryに保存する。

### 4.1 保持するデータ

**ユーザープロフィール**

- 内容：目標・状況・興味・悩みを整理したもの
- 取得元：3.2 ニーズの整理と保存
- 更新：対話のたび
- 参照できる人：本人のみ

**対話ログ**

- 内容：ユーザーとAIのやり取り
- 取得元：3.1 ニーズ把握の対話
- 更新：対話のたび
- 参照できる人：本人のみ

**提案履歴**

- 内容：提案したサービス、おすすめの理由、提案日時、その時点のユーザープロフィール、承諾の有無
- 取得元：3.4 提案の生成、3.5 提案したサービスを開く
- 更新：提案・承諾のたび
- 参照できる人：本人のみ

**行動履歴・端末の利用状況**

- 内容：本サービス内の操作の記録と、端末の利用状況
- 取得元：アプリと端末（ユーザーの同意を得て収集）
- 更新：収集のたび
- 参照できる人：本人のみ

**Webサービス候補データ**

- 内容：提案対象となるWebサービスの名称、用途、対象者、料金区分、URL。当面はLINE・Instagram・X・ChatGPTの4サービスに限定する
- 取得元：チームが手作業で作成
- 更新：対象サービスを増やすとき
- 参照できる人：全ユーザー共通（読み取りのみ）

### 4.2 扱わないデータ

- 提案先Webサービスのパスワード・Cookieは取得・保存しない
- 氏名・連絡先・住所・位置情報など、個人を特定できる情報は保存しない
- あるユーザーのデータを、他のユーザーの提案に使わない

### 4.3 データパイプライン

BigQuery上で、データを raw（生データ）→ staging（整形）→ mart（集計）の3層に分けて管理する。アプリはrawに書き込むだけとし、整形・集計はBigQuery内で行う。

```
アプリ（バックエンド）
   │ 発生したデータをそのまま追記する（上書き・削除はしない）
   ▼
raw（生データ）
   │ ビューで型の統一・重複除去・最新版の抽出を行う（常に最新）
   ▼
staging（整形）
   │ スケジュールクエリで1時間ごとに集計する
   ▼
mart（集計）
   │
   ▼
バックエンド（ニーズ変化の検知・提案の振り返りに使う）
```

**raw（生データ）**：4.1のデータを、発生した時点のまま追記で保存する

- raw_conversation_logs：対話ログ（1回の質問・回答ごとに1行）
- raw_user_profiles：承認されたユーザープロフィール（承認・更新のたびに1行、版として残す）
- raw_proposals：提案（1回の提案のサービスごとに1行）
- raw_proposal_acceptances：提案の承諾（承諾のたびに1行）
- raw_activity_events：行動履歴・端末の利用状況（1操作・1計測ごとに1行）
- service_catalog：Webサービス候補データ（チームが手作業で登録）

**staging（整形）**：アプリが画面表示に使う形に整える。ビューで作るため、rawに書き込まれた内容がすぐに反映される

- stg_user_profiles_latest：ユーザーごとの最新のプロフィール（3.3・3.6で使う）
- stg_proposal_history：提案・承諾・その時点のプロフィールを結合した履歴（3.7で使う）

**mart（集計）**：スケジュールクエリで1時間ごとに作り直す

- mart_user_activity_daily：ユーザー・日ごとの行動量（操作回数、承諾したサービス、利用した時間帯など）。AIによるニーズ変化の判定（3.6）の入力に使う
- mart_service_performance：サービスごとの提案回数・承諾回数・承諾率。提案の妥当性の確認に使う

## 5. ユーザーフロー

ユーザー自身が行う操作を示す。

1. アプリを開き、AIとの対話を始める
2. AIの質問に回答する
3. 整理されたニーズ（目標・状況・興味・悩み）を確認し、誤りがあれば修正して承認する
4. 提示された提案（サービス名・理由・URL）を見て、使うものを承諾する
5. 開いたサービスに、自分で登録・ログインして使い始める
6. 目標・状況が変わったら、その変化をAIに伝える（伝えなくても、システムが行動履歴から変化を検知する場合がある）
7. 提案履歴で、以前のニーズと提案を振り返る

ステップ3とステップ4はユーザーの操作が必要で、ここで止まるとシステム側の後続処理は進まない。

## 6. 業務要件（システムフロー）

システム側が行う処理を、処理順に示す。

1. 目標・状況・興味・悩みを聞き出す質問を生成し、ユーザーの回答を受け取る
2. 回答を4項目に整理し、確認用に提示する
3. ユーザーの承認を受けて、ユーザープロフィールを保存する（ユーザーフロー ステップ3）
4. ユーザープロフィールをもとにWebサービス候補を検索し、合う順に並べる
5. 上位の候補を、おすすめの理由とともに提示する
6. ユーザーが承諾した提案のサービスをリンクで開く（ユーザーフロー ステップ4）
7. 行動履歴・端末の利用状況を収集し、ニーズが変化したかをAIで判定する
8. 変化を検知した、またはユーザーから変化を伝えられたら、提案を作り直す（ユーザーフロー ステップ6）

## 7. アーキテクチャ

本サービスを構成する要素と、要素間の処理の流れを示す。インフラはすべてGoogleのサービスで構成する。具体的な実装方式は設計書で定める。

### 7.1 処理の流れ

**(1) ユーザーの入力を受け取り、画面に表示する**

```
ユーザー（Webブラウザ）
   │ 対話の回答・承認・変化の申告を入力する
   ▼
フロントエンド（各画面）
   │ 入力を送る ／ 表示用データを受け取る
   ▼
バックエンド
```

**(2) AIを呼び出す**

```
バックエンド
   │ 質問生成・ニーズ整理・候補比較・提案文生成・ニーズ変化の判定を依頼する
   ▼
AI（Gemini API）
   │ 結果を返す
   ▼
バックエンド
```

**(3) データを読み書きする**

```
バックエンド
   │ 各データを書き込む ／ 読み出す
   ▼
データストア（BigQuery）
```

**(4) 承諾したサービスを開く**

```
ユーザー（提案結果画面）
   │ 提案を承諾する
   ▼
提案先Webサービス（リンクから新しいタブで開く）
```

### 7.2 構成要素の役割

- **フロントエンド**：対話画面・ニーズ確認画面・提案結果画面・提案更新画面・提案履歴画面を表示する
- **バックエンド**：6章のシステムフローを実行し、AI・データストアとのやり取りを担う
- **AI（Gemini API）**：質問生成、ニーズの整理、候補の比較、提案文の生成、ニーズ変化の判定を行う
- **データストア（BigQuery）**：4.1のデータを保持する
- **提案先Webサービス**：ユーザーが承諾したときにリンクで開く外部のWebサービス（LINE・Instagram・X・ChatGPT）。API連携は行わない
- **実行基盤（Cloud Run）**：フロントエンドとバックエンドを1つのCloud Runサービスとして稼働させる。リクエストがないときは停止するため、無料枠に収めやすい

## 8. 非機能要件

### 8.1 一般

- **実行環境**：スマートフォンとPCのWebブラウザで表示できること（対応端末・ブラウザの具体は未確定）
- **応答時間**：対話の1往復と提案の生成の目標時間は未確定
- **同時利用者数**：同時1名で動作すればよい（動作確認を想定）
- **提案件数**：1回の提案は3件以内とする（画面で一度に読める範囲とするため）
- **コスト**：各サービスの無料枠を超える構成は採用しない
- **リージョン**：東京（asia-northeast1）

### 8.2 セキュリティ

- **通信**：ブラウザとバックエンド間の通信はHTTPSで暗号化すること
- **APIキーの管理**：Gemini APIのキーはバックエンドだけで保持し、ブラウザに渡さないこと
- **アクセス制御**：ユーザープロフィール・対話ログ・提案履歴・行動履歴は、本人だけが参照できること
- **行動履歴の収集**：ユーザーの同意を得てから収集を始め、ユーザーがいつでも止められること
- **個人情報**：4.2のとおり、個人を特定できる情報は保存しないこと

## 9. 用語定義

- **Webサービス**：ブラウザやアプリを通じて提供されるソフトウェアや機能（チーム定義 2026-10-19）
- **ニーズ**：ユーザーの目標・状況・興味・悩み。本サービスはこの4項目でニーズを捉える
- **ユーザープロフィール**：ユーザーが承認した、ニーズ4項目の内容（3.2）
- **ニーズの変化**：ユーザープロフィールのいずれかの項目が、前回の提案時点と変わること。AIが行動履歴から判定するか、ユーザーが申告する（3.6）
- **対話ログ**：ニーズを聞き取る際の、AIの質問とユーザーの回答の記録（3.1）
- **行動履歴**：本サービス内でのユーザーの操作と、端末の利用状況の記録。ユーザーの同意を得て収集する
- **Webサービス候補データ**：提案の候補となるWebサービスの一覧。当面はLINE・Instagram・X・ChatGPTの4件
- **提案**：サービス名・おすすめの理由・URLを1組とした出力。1回に最大3件（3.4）
- **承諾**：ユーザーが提案を受け入れ、そのサービスを開く操作（3.5）
- **提案履歴**：過去の提案・承諾の有無・その時点のユーザープロフィールの記録（3.7）
- **raw／staging／mart**：BigQuery上のデータの3層。rawは生データ、stagingは画面表示用に整えたもの、martは集計結果（4.3）
- **ジャービス型**：複数のサービスを一つの窓口からまとめて操作する構想。本サービスでは対象外（2.4）
