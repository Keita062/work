# AsIs/ToBe/Gap/Issue/Solution 分析フレームワーク

> 出典：`mbk-digital/set_up`リポジトリのナレッジベースより、案件に依存しない技術知見として移植（2026-10-20）。

## 対象タスク

課題整理・改善提案・目標設定など「現状と理想のギャップを埋める」系のドキュメントを作成する際に、毎回このフレームワークで構成する。案件名を問わず汎用的に使う思考の型。

## 各要素の定義

| 要素 | 問い | 内容 |
|---|---|---|
| ToBe（あるべき姿） | どうなりたいか | 理想状態を定義する |
| AsIs（現状） | なりたい姿に対して、いまはどうなのか | ToBeの**各項目に1対1で対応させて**現状を書く |
| Gap（ギャップ） | ToBe−AsIsの差分は何か | 理想と現状の差分そのもの |
| Issue（ギャップの要因） | Gapはなぜ生じているのか | Where（どこに課題があるか）→Why（それはなぜか）の順で深掘りする |
| Solution（解決策） | Issueを解決する方法は何か | Issueに対応する具体策 |

## 具体例

- **ToBe**：分析の着想から実行までを独力で実行できている
- **AsIs**：分析の着想から実行までを独力で実行できず、上長のサポートを必要としている
- **Gap**：上長のサポートなく、分析の着想から実行までを独力で実行することができない
- **Issue**
  - Where：どこに課題があるのか？→ 分析の着想から実行の工程をブレイクダウンすると、XXX。そのうち、YYYの工程に課題がある
  - Why：それはなぜか？→ ZZZができていないのが要因
- **Solution**：Issue（ZZZができていないこと）を解消するための具体策

## 使う上での注意点（本人フィードバックより）

- **ToBeとAsIsは必ず同じ粒度・同じ項目単位で対応させる**。ToBeで書いた項目に対応するAsIsが書かれていない、あるいは項目の粒度がズレている状態は誤り。ToBeの各文に対して「それに対応する現状はどうか」を1文ずつ書けるかを確認する
- Gapは「ToBeとAsIsの差分を言い換えただけの文」になりがちだが、それで良い（Gap自体に新しい情報を足す必要はない。ToBeとAsIsを引き算した結果を一文にする）
- IssueはGapをそのまま「なぜ？」と一段深掘りするだけで終わらせず、必ずWhere（どの工程・どの箇所に課題があるか、対象をブレイクダウンして特定する）→Why（その工程でなぜできていないのか）の2段階で書く。Whereを飛ばしてWhyだけ書くと、対策が的外れになりやすい
- Solutionは、Issueで特定した「Why」に直接効く打ち手にする。Gapに対して直接対策を書かない（Issueを経由させる）
- **ToBe／AsIs／Gapは案件・テーマ全体で1つずつにする**。「論点ごとにToBe/AsIsのペアを複数作る」のは誤り（ToBeを3つの小テーマに分けて、それぞれにAsIs/Gapを対応させる、といった構成をやりがちだが、これは論点を分割しすぎている）。ToBeは案件の理想状態を1つの文（または1セットの状態）として書き、AsIsもそれに対応する現状を1つ書く。Issueで初めてWhereとして複数の工程・箇所に分解し、Solutionで複数の解決策に枝分かれさせる。「複数に分けたくなる粒度」はToBe/AsIsではなくIssueのWhereで扱う
- Solutionは1つとは限らない。Issueで特定した複数のWhy（複数の課題箇所）に対応して、Solutionが複数の柱（例：目標設定の手順を整備する／モニタリング体制を整備する）に分かれるのは正しい構成
- ToBeが「①、②、③」のように複数要素を1文にまとめている場合、AsIsも**同じ①②③の構造・同じ語順で、それぞれを直接否定する形**で書く。例：ToBeが「③投資判断を数字で下せる状態になっている」なら、AsIsは「③投資判断を数字で下せる状態になっていない」と直接対応させる。AsIsを「探索分析は実施済みで〜」のような別の切り口の説明から書き始めると、読み手からは①②③のどれに対応するAsIsなのかが分からず、対応していないように見える。まず①②③をそのまま否定した1文を書き、その後の補足でなぜそうなっているか（要因の匂わせ程度）を各項目にひも付けて添える

## 適用範囲

課題整理・改善提案・目標設定ドキュメント全般（案件のKGI/KPI設計、個人の評価・育成、業務改善提案など）に応用できる。
