# openpyxlで作成したExcelの数式・書式の落とし穴

> 出典：`mbk-digital/set_up`リポジトリのナレッジベースより、案件に依存しない技術知見として移植（2026-10-20）。

## 対象タスク

openpyxlでExcelファイルを新規作成・更新するタスク全般。特に「既存の集計表に新しい年度の列・行を追記する」「サマリシートから計算シートを串刺し参照する」といった作業のときに、毎回このチェックを通してから納品する。

openpyxlは**書き込んだ数式を一切検証しない**（文字列としてそのままXMLに埋める）。またセルに値を代入しても**書式は引き継がれない**。このためExcelで開くまで壊れていることに気づけない、という事故が起きやすい。

## 1. 数式の落とし穴

### 1-1. 複数シート参照のレンジで、右端にもシート名を書いてしまう

一番やりがちで、かつ一番被害が大きい。

```python
# NG: 範囲の右端にもシート名が付いている
ws['B6'] = "=SUM('01_計算過程'!C23:'01_計算過程'!I23)"

# OK: シート名は範囲の左端に一度だけ
ws['B6'] = "=SUM('01_計算過程'!C23:I23)"
```

ExcelのUIに手入力する分にはNG側も受け付けて自動で正規形に直してくれるが、**xlsxファイルに格納する形式としては正規形しか許されない**。openpyxlはそのまま書き込むため、Excelで開くと「ファイルの一部に問題が見つかりました」という修復ダイアログが出て、該当セルの数式が削除される。Googleスプレッドシートにインポートした場合はエラー値になる。

シート名に日本語・数字始まり（`01_計算過程`のようにシート名が数字で始まる場合）・スペースが含まれるとシングルクォートでの囲みが必須になり、この形を書いてしまいやすい。

### 1-2. 未入力判定を `=0` で書いてしまう

「まだ値が入っていない年度は空欄にする」という意図の判定を、`=0`との比較で書くと意図がずれる。

```python
# NG: 0という実データと、未入力を区別できない
'=IF(\'02_詳細\'!B39=0,"",\'02_詳細\'!B39)'

# OK: 空セルは "" と等しいので、未入力判定は "" で行う
'=IF(\'02_詳細\'!B39="","",\'02_詳細\'!B39)'
```

Excelでは空セルは `=""` でも `=0` でもTRUEになるため一見どちらでも動くが、`0`という実データが入った瞬間に「未入力」と誤判定して空欄にしてしまう。表内で判定方法が混在していること自体が後から読む人の混乱のもとなので、`=""` に統一する。

### 1-3. 計画値のない年度を、空セル参照の0として計算してしまう

「計画」と「実績」を並べる表で、計画値が存在しない年度の乖離を `=実績-計画` と素直に書くと、空セル参照が0とみなされて**乖離＝実績そのまま**という誤った数字が表示される。数式としてはエラーにならないので気づきにくい。

```python
# OK: どちらかが空なら結果も空にする
'=IF(OR(B9="",C9=""),"",C9-B9)'
```

同じ表の中で、ある行は空判定あり・別の行は判定なし、という不統一が起きていないか必ず確認する。

### 1-4. 単一セル参照の絶対／相対が混在する

`='01_計算過程'!B12` と `='01_計算過程'!$B$12` が同じブック内に混在していると、後からコピーした人が壊す。前提値のような「1箇所を全員が参照する」セルは絶対参照に統一しておく。

## 2. 書式の落とし穴

### 2-1. 値を代入しても書式は引き継がれない

`ws['G11'] = 100` としても、隣の `F11` が持っている背景色・表示形式・太字・罫線は一切コピーされない。**年度列や年度行を追記するタスクでは、書式の付け忘れが必ず起きると思っておく。**

特に見落としやすいのが以下。

- **背景色**：入力値セルのグレー塗り分けなど、「どこが手入力でどこが数式か」を示す意味を持っていることが多い
- **表示形式**：これだけは**表示上の実害が出る**。`0.0%` を付け忘れると `0.743` が `#,##0` で丸められて **「0」と表示される**。色や太字と違い、数字そのものが読めなくなるので最優先で確認する
- **太字**：合計行・合計列の強調
- **罫線**

### 2-2. 書式をコピーするときは `copy.copy` する

スタイルオブジェクトを共有すると、片方を変えたときに他方も変わる。フォントの一部だけ変えたい場合も必ずコピーしてから差し替える。

```python
import copy
f = copy.copy(ws['G15'].font)
f.bold = True
ws['G15'].font = f
```

### 2-3. 再計算を強制する

openpyxlが保存したファイルにはキャッシュ値が残らないため、値をキャッシュしているビューアでは0や空に見えることがある。保存前に以下を入れておく。

```python
wb.calculation.fullCalcOnLoad = True
```

## 2-4. 他ブックのデザインに合わせるときは、書式を目視で拾わずスクリプトで抽出する

「このファイルと同じ体裁にしてほしい」という依頼は頻出するが、**見た目から書式を推測すると必ず取りこぼす**。フォント名・罫線の色・ヘッダの配色・グリッド線の表示設定は画面を見ても正確な値が分からない。参照元を`load_workbook`で開き、代表セルの属性をそのまま吐き出して定数化する。

```python
for a in ('A1', 'A4', 'A5', 'A6', 'B6', 'A10'):   # タイトル/見出し/ヘッダ/データ/注釈
    c = ws[a]
    b = c.border.left
    print(a, b.style, getattr(b.color, 'rgb', None),
          c.font.name, c.font.size, c.font.bold, getattr(c.font.color, 'rgb', None),
          c.alignment.horizontal, c.fill.start_color.rgb if c.fill.fill_type else None)
print('gridlines', ws.sheet_view.showGridLines)
```

特に見落としやすいのが次の2つ。

- **`ws.sheet_view.showGridLines`**：整った資料はほぼ例外なく`False`。これだけで印象が大きく変わるのに、セルの書式を見ていても気づけない
- **罫線の色**：`thin`でも色が`FF000000`（黒）か`FFCCCCCC`（薄グレー）かで密度感が別物になる。`style`だけ揃えても似ない

あわせて、ブック全体で書式が1系統とは限らない点にも注意する。後から追加されたシートだけ別系統になっていることがあるので（SBおうち割v12では`00〜04`がBIZ UDGothic＋濃グレーヘッダ、後付けの`05_シミュレーション`だけMS Pゴシック＋薄グレーヘッダだった）、**どのシートを正本にするかを決めてから抽出する**。

使用されている値を一覧化して全体像を掴むのも有効。

```python
# ブック内で実際に使われている塗り・表示形式・フォントサイズを数える
```

`grep -o "fill[0-9A-F]\{8\}" dump.txt | sort | uniq -c` のように、ダンプ済みテキストに対して集計するだけでも「この2色が主役」「medium罫線は1つも使っていない」といった設計意図が読み取れる。

## 2-5. 他シートが絶対参照している行はずらせない ― 上部の作り替えは「行数固定の枠」として設計する

サマリ以外のシートから`'01_前提'!$E$28`のように絶対参照されているブロックは、**行を1つ挿入するだけで参照先が全部ずれる**。openpyxlは行挿入時に他シートの数式を追従してくれないため、気づかないまま単価が別の行を指す事故になる。

対策は、参照されているブロックの開始行を固定したまま、**その手前の行数の中でレイアウトを組むこと**。

```python
# 01_前提 の r14以降（単価一覧・件数入力欄・金額入力欄）は 02_効果算出 が絶対参照している。
# よって作り替えられるのは r1〜r13 の13行だけ、という制約のもとで設計する。
for r in range(1, 14):
    for c in range(1, 7):
        ws.cell(row=r, column=c).value = None
```

このとき起きやすいのが、**見出しと表ヘッダの行番号が衝突して見出しが消える**という失敗。使える行数がギリギリだと配置を詰めた結果ぶつかる。

```python
# NG: 見出しを書いた直後に、同じ行から表を作り始めている
put(ws, "A7", "■ お金の流れ", HEAD_F)
table(ws, 7, 12, 1, 6)      # r7がヘッダ行として上書きされ、見出しが消える

# OK: 見出し → ヘッダ → データ → 注釈 の行番号を先に紙の上で数えてから書く
put(ws, "A6", "■ お金の流れ", HEAD_F)
table(ws, 7, 12, 1, 6)
```

**行数が足りないと分かった時点で、削る対象は注釈**。見出しや定義そのものを削ると情報が落ちる。注釈は他シートに同じ記述があることが多いので、重複を確認してから落とす。

なお、作り替えた範囲には前の版の罫線・背景が残るため、値を消すだけでは不十分。罫線・塗り・フォント・配置を素に戻す`reset()`を通してから新しい書式を当てる。

## 3. 検出スクリプト

納品前に必ずこの2つを通す。目視では絶対に見つからない。

### 3-1. 不正な複数シート参照レンジの検出

openpyxlの`load_workbook`経由ではなく、**生XMLを見る**のがポイント（パーサを通すと正規化されて見えなくなる場合がある）。

```python
import zipfile, re
z = zipfile.ZipFile(PATH)
for n in z.namelist():
    if n.startswith('xl/worksheets/sheet'):
        for m in re.finditer(r'<f>(.*?)</f>', z.read(n).decode('utf-8')):
            f = m.group(1)
            # 範囲の途中にシート名が再登場していないか
            if re.search(r"![A-Z]+\d+\s*:\s*(&apos;|')", f):
                print('不正レンジ:', n, f)
            # シート名にクォートが必要なのに付いていないか
            if '!' in f and "'" not in f and '&apos;' not in f:
                print('要確認(クォートなし参照):', n, f)
```

### 3-2. 行方向・列方向の書式の一貫性チェック

「同じ行なら書式も揃っているはず」という前提で多数決を取り、外れ値だけを報告させる。追記漏れは必ず「1〜数セルだけ周りと違う」形で現れるので、この方法でほぼ確実に拾える。

```python
import openpyxl
from collections import Counter

def sig(c):
    f = c.fill
    return (f.start_color.rgb if f.fill_type else None, c.font.bold, c.number_format)

wb = openpyxl.load_workbook(PATH)
for ws in wb.worksheets:
    for r in range(1, ws.max_row + 1):
        cells = [ws.cell(r, c) for c in range(2, ws.max_column + 1)
                 if ws.cell(r, c).value is not None]
        if len(cells) < 4:
            continue
        cnt = Counter(sig(c) for c in cells)
        common, n = cnt.most_common(1)[0]
        if n < len(cells):
            odd = [(c.coordinate, sig(c)) for c in cells if sig(c) != common]
            if len(odd) <= 2:   # 外れが多い行は元々そういう構造なので除外
                print(f'{ws.title} 行{r} 多数={common} 例外={odd}')
```

注意点として、`len(odd) <= 2` の足切りを入れると、**半分近くが抜けている列（例：7列中3列が塗り漏れ）は検出から漏れる**。しきい値を変えて2回流すか、列方向でも同じチェックを流すこと。

## 4. 修正後の検証

**書式や数式の形を直しただけでも、必ず計算結果が変わっていないことを確認する。** Excelを開かずに検証するには、Pythonで同じ計算を独立に組み直し、修正前に記録してあった数値（Context Vaultの進捗記録など）と突き合わせる。

この突き合わせができるように、**計算結果の主要な数値はContext Vaultに残しておく**ことが結果的に一番効く。
